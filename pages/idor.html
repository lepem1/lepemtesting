IDOR Testing Lab

Practise identifying broken object-level authorization using eight isolated simulations.

Simulation only: These buttons run local JavaScript tests. They do not contact a real server, use Burp Suite, or prove that any live website is vulnerable. The simulated server checks whether the signed-in user owns the resource.

Test accounts: Account A has ID user-100. Account B has ID user-200.

Tests not run yet.

1. Numeric IDOR

Scenario: a profile endpoint identifies profiles with numeric IDs.

Request example: GET /api/profiles/200

Test: Account A attempts to read Account B's profile by its numeric ID.

2. UUID / unpredictable ID

Scenario: a document uses a UUID instead of a sequential number. Unpredictable IDs do not replace authorization checks.

Example: GET /api/documents/doc-b7

3. Nested resource IDOR

Scenario: a comment is requested under a particular project. The server must verify access to both the project and comment.

Example: GET /api/projects/project-A/comments/comment-B

4. API object access

Scenario: an API returns a user's private settings. The API must check the authenticated user's permission.

Example: GET /api/users/user-200/settings

5. File / document access

Scenario: a private report belongs to Account B. Knowing its file identifier should not grant access.

Example: GET /api/files/report-B

6. Invoice / order access

Scenario: Account A tries to view an order belonging to Account B. Private order details must remain restricted.

Example: GET /api/orders/order-B

7. Role / function authorization

Related access-control test: Account A attempts an administrator-only operation. This is generally called broken function-level authorization (BFLA), rather than a classic IDOR.

Example: POST /api/admin/reports

8. Export / download access

Scenario: Account A requests a private export generated for Account B. The download endpoint must check ownership or explicit permission.

Example: GET /api/exports/export-B/download

What do the results mean?

PASS means the simulated server blocked the unauthorized request as expected.

FAIL means the simulated server returned protected data to the wrong account.

These results describe only the built-in simulations. To test a real application, use an authorized test environment and verify its actual server responses.
