IDOR Testing Lab

Learn how insecure object references happen, recognize common patterns, and assess access controls using applications and test accounts you own or are explicitly authorized to test.

What is IDOR?

Insecure Direct Object Reference (IDOR) is an access-control vulnerability. An application identifies a resource using an ID or another reference but fails to verify that the current user is allowed to access that resource. 

Example URL:
https://lab.example.test/api/profile/1001

Security question:
Does the server verify that the signed-in user
is allowed to access profile 1001?
Changing an ID is not automatically a vulnerability. The issue exists when the server grants unauthorized access to the referenced resource.

IDOR patterns

The following are eight common testing categories and related object-authorization scenarios.

TYPE 01

Numeric IDOR

Resources use sequential identifiers such as user IDs or record numbers.

/api/profiles/1001
TYPE 02

UUID Reference

Resources use UUIDs or long opaque identifiers but still lack authorization checks.

/api/documents/{document-uuid}
TYPE 03

Nested Resource IDOR

A child object is accessed through a parent, such as a project's task.

/api/projects/{project}/tasks/{task}
TYPE 04

API Object Access

An API returns or modifies another user's object without checking ownership.

GET /api/orders/{order-id}
TYPE 05

File or Document Access

Private documents or attachments are exposed by predictable references.

/documents/{document-id}
TYPE 06

Invoice or Order Access

Financial or purchase records can be viewed by users who are not authorized.

/api/invoices/{invoice-id}
TYPE 07

Role / Function Access

Related access-control testing checks whether ordinary users can invoke privileged functions. This is often called BFLA, rather than IDOR.

POST /api/admin/reports
TYPE 08

Export and Download Access

Exports or generated reports can reveal another user's private information.

/api/exports/{export-id}

How many types?

8 categories

These are eight useful learning categories, not an official or exhaustive count. IDOR is one form of broken object-level authorization, and real applications can have many variations.

1. Numeric IDOR

Goal: Verify that records are restricted to authorized users.

  1. Use a test application with two accounts you control, Account A and Account B.
  2. Sign in as Account A and open a record owned by A. Record its identifier.
  3. Sign in as Account B and request A's record using the application's normal interface or a request captured in Burp.
  4. Confirm that the server denies access to the record. A denial should not disclose private record contents.

2. UUID Reference

Goal: Check whether opaque identifiers are incorrectly treated as authorization.

  1. Create two private documents in your own test application, each owned by a different test account.
  2. Observe how the application references each document.
  3. While signed in as the other account, test access to the second document in your lab.
  4. Verify that access is denied even when the requester knows the document's identifier.

UUIDs can make identifiers harder to guess, but they do not replace authorization checks.

3. Nested Resource IDOR

Goal: Verify ownership of both parent and child resources.

  1. Create two separate projects with separate test users.
  2. Identify the project and task relationships in your own application's normal requests.
  3. Test whether an account can access a task that belongs to a project it cannot access.
  4. Verify that the server checks the entire resource relationship, not just whether the task exists.

4. API Object Access

Goal: Check authorization on API read and write operations.

  1. Use an API and test records you own or are permitted to assess.
  2. Capture a normal read request in Burp Proxy's HTTP history.
  3. Repeat the test using a second authorized test account and a record belonging to the first.
  4. Where permitted, test update operations against your own disposable test records, then verify that unauthorized changes are rejected.

Check reads, updates, and deletions separately: each operation needs appropriate authorization.

5. File or Document Access

Goal: Verify that private files are not accessible to unrelated accounts.

  1. Upload harmless test files through your lab application using two test accounts.
  2. Observe how the app generates authenticated download links or file requests.
  3. Check whether the other account can access a private file through the app's authorized test workflow.
  4. Verify access control at the file-serving endpoint or storage layer, not only in the user interface.

6. Invoice or Order Access

Goal: Ensure customers only see their own transactions.

  1. Create fictional orders or invoices in a test environment.
  2. Use each test account to view its own transaction.
  3. Check whether one account can retrieve another account's transaction in the lab.
  4. Verify that both the record details and downloadable invoice are protected.

7. Role and Function Access (related BFLA testing)

Goal: Confirm that privileged functions require the appropriate role.

  1. Set up an administrator account and a regular account in a lab you control.
  2. Document which actions each role is meant to perform.
  3. Use the regular account to test a privileged action through the application's normal workflow.
  4. Verify that the server rejects the action regardless of whether the UI hides the relevant control.

This is related access-control testing, but it is not necessarily an IDOR vulnerability.

8. Export and Download Access

Goal: Protect generated reports and exports.

  1. Generate separate test exports for two accounts.
  2. Observe the normal process for checking export status and downloading a completed export.
  3. Test whether an account can access another account's export within your authorized lab.
  4. Verify authorization at both the export-status and download endpoints.
How to report a confirmed issue: document the affected endpoint, the test accounts and roles, the expected versus actual authorization behavior, and the minimum evidence needed to demonstrate impact. Avoid collecting unrelated private data.

Prevention checklist

  • Enforce object-level authorization on the server for every request.
  • Check ownership and tenant boundaries for each resource.
  • Apply authorization to read, update, delete, export, and download operations.
  • Do not rely on hidden buttons, unpredictable IDs, or client-side checks.
  • Write automated tests for access by unauthorized users.
