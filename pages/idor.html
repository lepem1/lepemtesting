IDOR Testing Lab

Learn how insecure direct object references and broken object-level authorization can expose data belonging to another user. Run each demonstration, inspect the API response, and understand the expected security behavior.

Controlled simulation

This lab uses fictional records. The secure mode returns a simulated authorization denial; vulnerable mode intentionally returns fictional test data. Neither mode accesses a real account or database.

How the lab works

IDOR is commonly used to describe a situation where an application lets a user access another user's object by changing or supplying an object identifier without properly checking authorization.

Account A — Current user

Demo ID: user-100

Role: ordinary user

Can access its own authorized records.

Account B — Other user

Demo ID: user-200

Role: ordinary user

Owns the private demo records used in these tests.

API endpoint
POST /api/idor-lab

Secure mode should return HTTP 403 when Account A requests Account B's private resource.

Individual IDOR tests

Run each test separately to understand the scenario and inspect its HTTP request in Burp Suite.

TEST 01

Numeric IDOR

Not run

Numeric identifiers are often used for profiles and records. A server must not assume that knowing another record's ID grants permission to read it.

Example endpoint GET /api/profiles/200

Simulated object: profile-200

TEST 02

UUID / unpredictable ID

Not run

Random-looking IDs can make guessing harder, but they are not an authorization system. The server still needs to verify access.

Example endpoint GET /api/documents/doc-b7

Simulated object: document-b7

TEST 03

Nested resource IDOR

Not run

A comment, task, or attachment may belong to a parent project. Authorization should cover both the parent and the requested item.

Example endpoint GET /api/projects/project-A/comments/comment-B

Simulated object: comment-b

TEST 04

API object access

Not run

An API may return private settings or account details. Hiding a button in the frontend is not enough; the backend must authorize the request.

Example endpoint GET /api/users/user-200/settings

Simulated object: settings-200

TEST 05

File / document access

Not run

Private reports and documents should only be returned to authorized users. A predictable filename or a copied file identifier should not bypass the permission check.

Example endpoint GET /api/files/report-B

Simulated object: report-B

TEST 06

Order / invoice access

Not run

Order history, invoices, and payment records can contain private information. The server should verify who owns the order or has been explicitly authorized to view it.

Example endpoint GET /api/orders/order-B

Simulated object: order-B

TEST 07

Admin function access

Not run

This is a related access-control check, usually called broken function-level authorization (BFLA). An ordinary account should not be able to perform administrator-only operations.

Example endpoint POST /api/admin/reports

Simulated operation: admin-report

TEST 08

Export / download access

Not run

A private export may be stored separately from the page that requested it. Its download endpoint must still verify authorization.

Example endpoint GET /api/exports/export-B/download

Simulated object: export-B

How to inspect requests in Burp Suite

  1. Deploy this page and the API endpoint to your Vercel project.
  2. Open the page in a browser configured to use Burp's proxy.
  3. Open Proxy → HTTP history in Burp Suite.
  4. Select a simulation mode, then click a test's Run test button.
  5. Find POST /api/idor-lab. Inspect the JSON request body and the JSON response.

The actual lab request is sent to /api/idor-lab. The other paths shown on the test cards are illustrative scenarios, not separate live endpoints.

Understanding the results

  • HTTP 403 in secure mode: the simulation denied the request, as expected.
  • HTTP 200 in vulnerable mode: the simulation returned fictional data to demonstrate the risk.
  • HTTP 400: the endpoint rejected the supplied input.
  • HTTP 404 or 405: check the deployed API path, file name, and HTTP method.
  • Network error: check the browser Network panel, Vercel deployment logs, and Burp proxy configuration.
Important

A successful simulation is not proof that a real application is secure or vulnerable. Real authorization testing requires a permitted test environment, appropriate test accounts, and verification of the application's actual server-side behavior.
